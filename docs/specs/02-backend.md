# Stage 2: local sync backend (Ktor Server)

## Goal

A small backend running locally (Docker or Gradle) that clients will sync todos with.
No authentication, a single shared list. No client changes in this stage.

## Modules

- `api` (new, Kotlin Multiplatform, same targets as `shared` + JVM): only `@Serializable`
  DTOs and route constants. No Compose/Room/Ktor dependencies. Used by `shared` (later) and
  `server`, so client and server share one compile-time checked contract.
- `server` (new, Kotlin JVM): Ktor Server (Netty), kotlinx.serialization, CallLogging + logback.
  Use the latest stable Ktor 3.x compatible with the project's Kotlin, via the version catalog.

## Contract

```kotlin
@Serializable data class TodoDto(
    val id: String,          // UUID, generated by the client
    val title: String,
    val description: String,
    val isDone: Boolean,
    val createdAt: Long,     // epoch ms, client clock
    val updatedAt: Long,     // epoch ms, client clock, used for last-write-wins
    val deletedAt: Long?,    // non-null = tombstone
)

@Serializable data class ChangesResponse(
    val items: List<TodoDto>,  // changed since `since`, tombstones included
    val revision: Long,        // cursor for the next pull
    val reset: Boolean,        // true = `items` is a full snapshot, client should replace its view
)
```

## Endpoints

| Method | Path | Behaviour |
|---|---|---|
| `GET` | `/health` | 200 OK |
| `GET` | `/todos?since={revision}` | changes with server revision > `since` (default 0 = everything). |
| `PUT` | `/todos/{id}` | idempotent upsert of a `TodoDto` (create, edit, toggle **and delete** via `deletedAt`). Returns the stored state. |

### Why delete is a `PUT` with `deletedAt` (not a separate `DELETE`)

One write path with one conflict rule. A delete is just a newer version of the todo that
happens to be a tombstone; last-write-wins then works the same for edits and deletes, and a
retried request is harmless.

### Server revision instead of time for `since`

The server keeps a global counter `revision`, incremented on every applied write, and stores
the revision of each todo. `since` refers to this counter, not to timestamps: device clocks
differ, a server-side counter cannot skip or repeat changes.

### Conflict rule (last-write-wins)

On `PUT`, apply the incoming todo only if there is no stored version or
`incoming.updatedAt > stored.updatedAt`. Otherwise (older or equal) ignore it.
Either way respond `200` with the stored (winning) version, so the client can reconcile.
A no-op write does not bump the revision.

### Server restart

Storage is in-memory (a map guarded by a `Mutex`). After a restart the revision starts again
from 0. If a client asks for `since` greater than the current revision, return everything
with `reset = true`. (Pending local changes are pushed by the client anyway, so nothing is lost.)

### Validation

`400` if the path id is not a UUID, path id ≠ body id, or title is blank on a non-tombstone.

## Running

- `./gradlew :server:run` → `http://localhost:8080`
- `Dockerfile` (fat jar + JRE image) and `docker-compose.yml` at the repo root:
  `docker compose up` → same port. Port configurable via env `PORT`.
- Logging: one line per request (method, path, status, duration).

## Tests (must pass) — `testApplication`, no real network

- `PUT` new todo → `GET ?since=0` returns it; revision increases.
- Same `PUT` twice → stored once, revision bumped only once (idempotent).
- `PUT` with older `updatedAt` → ignored, response contains the stored newer version.
- Tombstone `PUT` → appears in changes with `deletedAt`.
- `GET ?since=X` returns only later changes.
- `since` > current revision → full snapshot, `reset = true`.
- Validation cases → `400`.
- JSON round-trip of `TodoDto` / `ChangesResponse` (in `api`).

## Out of scope

Client networking, sync engine, SSE (stage 4), persistence to disk, auth.
